# 后续改进建议

## 1. 站点定位

当前建议定位为：**一份持续生长的个人成长档案，同时保留可实际使用的技术实验。**

这比“传统作品集”更适合当前阶段。它不要求先凑出许多项目，也不强迫内容全部围绕技术。求学经历、比赛感受、学习理解、科研过程和已经做出的功能可以共存。

内容与功能的关系建议保持为：

```text
个人成长档案（主线）
  ├─ 求学经历
  ├─ 比赛复盘
  ├─ 学习札记
  ├─ 科研手记
  └─ 阶段作品
       ├─ AI 热点
       └─ 万象索骥
```

## 2. 本轮审计结论

### 已修正

- 页面转场文档与实现不一致：原 `PageTransition` 为空，另有两套未挂载的重复组件；现已统一为取景框式转场。
- ESLint 基线存在 8 个错误和 5 个警告；已全部清理。
- 项目背景读取会触发级联渲染且没有预设下标校验；现已改为共享外部存储订阅。
- `/projects/explore` 和 `/projects/assistant` 在根布局的 `<main>` 内再次嵌套 `<main>`；已改正。
- 热点页声称保留 5 天，实际管道为 7 天；已统一。
- CI 定时计划当前被注释，但界面仍预测“下次更新时间”；已移除误导性承诺。
- Changelog 的 `feature` 公告和 `removal` 变更缺少类型/样式支持；已补齐。
- API 每次加载全部项目，且缺少请求长度、模式和分类校验；现已限制输入并只读取命中项目。
- `.env.example` 缺少 RAG/Trending Key，保留窗口仍为旧值；已同步。
- README 声称启用了 RLS，但初始化 SQL 没有执行；现已启用并保持 service role 服务端访问。
- 内页背景同质化；现按页面语义拆分为信号扫描、胶片档案、个人相纸和项目星图。

### 仍需关注

- 缺少自动化测试，SSE 标签协议主要依赖人工验证。
- RAG 全量重建先清空旧表再插入，新任务中途失败会造成线上数据短暂或长期缺失。
- 公开 API 没有速率限制、用户预算和调用指标。
- 内容数据仍散落在 TSX 常量和 JSON 中，不适合长期写作。
- `projects` 与 `embedding_chunks` 没有外键，数据完整性由脚本保证。
- 页面通过大量玻璃模糊和 Canvas 获得氛围，低性能移动设备仍需实测。

## 3. 个人内容系统：先轻后重

暂时不要搭建复杂 CMS。第一阶段使用仓库内纯 Markdown：版本可追踪、部署简单，也不会把写作与网页组件绑定。

建议目录：

```text
content/
  records/
    2026/
      competition-reflection.md
      first-research-note.md
```

建议 Front Matter：

```yaml
title: 一次经历的标题
date: 2026-08-21
summary: 比结果更值得留下的几件事
tags: [比赛, 协作, 复盘]
featured: false
draft: true
cover: /records/2026/article-name/cover.jpg
```

初期不设置分类，`tags` 也只负责展示，不提供筛选。内容积累后再根据真实文章决定是否形成栏目。

推荐页面：

- `/records`：按时间排列的全部记录，不先拆成多个频道。
- `/records/[...slug]`：文章详情，支持图片、公式、代码和表格。
- `/about`：个人事实，以及 `featured: true` 的真实经历。
- 首页：最近 3 条记录 + 1 条精选阶段作品。

当文章超过约 50 篇、需要手机端编辑或多人协作时，再评估 Headless CMS。

## 4. 视觉系统下一阶段

本轮建立了“取景框／胶片显影”视觉语言，后续应继续围绕内容，而不是继续堆特效。

优先级建议：

1. 为记录详情页设计稳定的阅读排版：正文宽度、行高、标题层级、脚注和图片说明。
2. 给成长记录增加胶片编号、拍摄时间式元数据和轻量时间轴。
3. 使用真实照片做少量封面；不要给每篇文章生成风格不一致的 AI 插图。
4. 在真实手机上检查玻璃模糊、Canvas、宠物和转场的组合性能。
5. 加入亮色“相纸模式”前，先确保暗色模式下长文阅读舒适。

页面转场应保持在约 0.7–1 秒。访问频繁的子页面可进一步缩短，且必须继续尊重 `prefers-reduced-motion`。

## 5. 未来的站内 LLM

不要把它做成独立的通用聊天框。更合适的角色是“站内向导”：帮助访客理解你的记录和查找内容。

推荐链路：

```text
Markdown / 项目说明 / 更新日志
  → 构建时提取纯文本和页面元数据
  → 按文章段落切块并生成向量
  → Supabase 独立 content_chunks 表
  → 检索 Top-K
  → LLM 回答
  → 每段结论附站内文章标题与链接
```

它可以回答：

- “他参加比赛后最大的感受是什么？”
- “最近在学什么？”
- “万象索骥是怎么实现的？”
- “有哪些与科研有关的记录？”

必须具备的约束：

- 只根据公开站内内容回答，不猜测私人经历。
- 每个事实结论带可点击来源。
- 无检索证据时明确说不知道。
- `draft: true` 的草稿永不进入索引。
- 个人内容索引与开源项目 RAG 分表、分 RPC，避免语料相互污染。

## 6. 工程路线图

### P0：公开推广前

- 为 `parseOptions`、`parseSuggestions`、`parseProjectRefs`、`stripTags` 增加单元测试。
- 为 `/api/projects` 增加速率限制、超时、调用指标和每日预算。
- RAG 重建改成 staging 表或带 `generation_id` 的原子切换，避免先删后写。
- 增加最小浏览器流程：导航转场、移动菜单、引导模式首轮、SSE 中断恢复。

### P1：开始持续写作时

- [x] 建立 `content/records`、Front Matter 读取与草稿隔离。
- [x] 增加 `/records` 与 `/records/[...slug]`。
- [x] 首页展示最近记录；档案页展示 `featured: true` 的真实经历。
- [ ] 增加 RSS、sitemap 和 Open Graph 图片。
- 为图片生成宽高、模糊占位和版权/来源字段。

### P2：内容形成规模后

- 上线带引用的站内 LLM 向导。
- 增加全文搜索和标签关系图，但避免用关系图取代正常导航。
- 根据真实访问数据决定是否引入 CMS、评论、订阅或多语言。

## 7. 不建议现在做的事

- 为了看起来像作品集而虚构项目、科研成果或比赛成绩。
- 在没有稳定文章之前先搭复杂后台、账号系统和评论系统。
- 让 LLM 读取未发布笔记或在没有引用时介绍个人经历。
- 为每个页面添加完全不同的动效；视觉差异应来自内容语义，交互规则仍需一致。
- 同时维护本地 JSON、数据库和组件常量三份文章源。个人文章以 Markdown 为唯一来源。
